# `data/`

Everything related to the project's datasets: code (schemas, scripts), runtime artefacts (raw downloads, lineage records, processed parquet).

## Layout

```
data/
├── __init__.py             marks the directory as a Python package so schemas/ can be imported
├── schemas/                pandera schemas applied at every pipeline boundary (code, gitted)
├── scripts/                placeholder for one-off data-preparation scripts (gitted)
├── raw/                    raw downloads written by src/data/downloaders/* (gitignored)
│   ├── _api_responses/     last 5 raw API responses per (source, series) for debugging
│   ├── ons/                CSV per ONS series after parsing + raw-schema validation
│   ├── boe/                CSV per BoE IADB series
│   ├── fred/               CSV per FRED series
│   └── boe_yc/             CSV per BoE GLC maturity (2y, 10y)
├── interim/                intermediate frames (gitignored; currently unused, reserved)
├── processed/              the final quarterly dataset, written by src/data/build_dataset.py
│   └── final_dataset.parquet
├── lineage/                JSON lineage record per artefact, written automatically (gitignored)
└── user-needs/             Sprint 1 ethics + user-needs docs (consent template, ethics form, personas, etc.)
```

## Refresh procedure

The pipeline is fully automated. From a fresh checkout:

```bash
make install        # python deps into the active venv
make data           # download - aggregate - engineer - quality - schema - save parquet
```

`make data` rewrites `data/raw/<source>/<series>.csv`, refreshes `data/raw/_api_responses/`, updates `data/lineage/<source>__<series>.lineage.json`, and writes `data/processed/final_dataset.parquet`. The pipeline is idempotent: running it twice produces an identical parquet (modulo any underlying revisions to ONS / BoE / FRED data between runs).

To refresh after a new ONS release without re-downloading the other sources, run a smaller scope manually:

```bash
.venv/bin/python -m src.data.downloaders.ons    # or call download_all_ons() in a session
make process                                    # re-run aggregation + engineer + save from cached raw CSVs
```

To reproduce inside a clean environment (e.g. on the examiner's machine):

```bash
docker compose build pipeline
docker compose run --rm pipeline                # runs `make data` inside the container
```

The host's `data/processed/`, `data/raw/`, `data/lineage/`, and `logs/` are volume-mounted, so the parquet appears on the host filesystem after the container exits.

## Lineage records

Every downloaded series writes a JSON record to `data/lineage/<source>__<series>.lineage.json`:

```jsonc
{
  "git_commit": "1c91147...",
  "output_path": "data/raw/ons/gdp_growth.csv",
  "parameters": { "cdid": "IHYQ", "dataset": "qna", "frequency": "quarterly", "url": "..." },
  "source": "ons:IHYQ",
  "timestamp_utc": "2026-06-15T11:16:17.842132+00:00",
  "transformations": ["http_get", "parse_ons_json", "validate"]
}
```

The records are the audit trail, they document what was downloaded, when, from where, and which version of the code did the work. They are gitignored (regenerated by every run), so the trail of record is the code (config + downloaders) plus the parquet.

## Schemas

Every data boundary is validated:

| Schema | Where it runs |
|---|---|
| `data/schemas/raw_ons.py`           | inside every ONS downloader after parsing |
| `data/schemas/raw_ons_gdp.py`       | available for the GDP-specific (date, gdp_growth) shape; used in tests |
| `data/schemas/raw_boe_rate.py`      | inside the BoE Bank Rate downloader |
| `data/schemas/raw_fred.py`          | inside FRED + BoE_YC downloaders |
| `data/schemas/processed_quarterly.py` | end of `build_dataset.py`, just before `to_parquet` |

The processed-quarterly schema is the contract for downstream modelling: 1 date + 17 data columns, all required, with deliberately generous range bounds whose only job is to catch obvious corruption (wrong units, flipped sign, all-zero column) rather than to characterise the data tightly.
